1. Purpose

A learning-first practice system for data structures and algorithms, taking the best from sites like LeetCode and HackerRank but focused on teaching rather than testing: a learner should get direct instruction (the Learning tab) before being asked to solve something. It is meant to grow into a multi-user, web-hosted system. Source: THOUGHTS, TODO.

2. Running it

CommandWhat it does
make toolchain-depsRuns scripts/toolchain-deps.sh, which every target that needs Node runs first (install, run, dev, sandbox-test). It installs what docs/deploy-vps.md §1–§2 list, plus LDC for D, if it's missing:
  • g++, default-jdk-headless, python3, ldc, curl and xz-utils from apt;
  • Node 22.23.4 from nodejs.org into /usr/local, checked against nodejs.org's SHASUMS256.txt and the hash recorded in the script, but only if the node your PATH finds first is older than 22 (Node 20 reached end-of-life in April 2026).
It uses sudo only when it has something to install. Unlike sandbox-deps, it stops make if it can't fix things, because the server can't start without these. One case it can't fix: an older node still first on your PATH. It says which one and where to look. It also warns, without stopping, about a node that's an odd-numbered release (never LTS), past its end of life, or within 90 days of it, using end dates copied from the Node.js Release team's schedule.json (read 2026-11-02). Node 22, which the VPS uses, ends on 2027-04-30, so the warning starts in February 2027.
make installRuns npm install if node_modules is older than package.json.
make sandbox-depsRuns scripts/sandbox-deps.sh, which make run and make dev also run first. It checks that the judge's sandbox works (about 0.1 s, no root). If it doesn't, it fixes what it can, using sudo, which may ask for your password, and saying what it runs. It installs bubblewrap if missing, and libseccomp-dev, which the server needs to build the sandbox's seccomp filter. If Ubuntu's AppArmor restriction on user namespaces is what stops bubblewrap, it installs apparmor-profiles and loads Ubuntu's bwrap-userns-restrict profile. That's a machine-wide change, made only in that case: afterwards any user's bwrap may create user namespaces. If it can't fix things, it warns and lets the server start, and the server then refuses to judge. Run as root, it checks as nobody, like the server does when it's root, because root may create user namespaces even where AppArmor blocks everyone else. Until 2026-11-02 its second check ran as root, so on the VPS it blamed something other than AppArmor and didn't load the profile.
make runStarts the server in the foreground (PORT=3000 node server.js; Ctrl-C stops it). In the background it polls the server with curl every 0.2 s until it answers, then opens it with xdg-open (your default browser). If the server hasn't answered within about OPEN_WAIT seconds (±1 s) (default 30; e.g. make run OPEN_WAIT=60), it prints a message and gives up on the browser. Override the port with make run PORT=8080. Needs curl and xdg-open (package xdg-utils); the cloud environment has no xdg-open, so there the browser step fails and the server still runs.
make devStarts the server under nodemon, which restarts it whenever a .js, .mjs, .cjs or .json file changes, except under users/ (set in package.json → nodemonConfig). Opens the browser once at startup, the same way as make run; restarts don't open it again.
make sandbox-testRuns judge/sandbox-selftest.js, the judge's escape test (about 30 s). Each probe is a hostile submission, and the result says whether it was contained or ESCAPED. A probe can also say skipped, when this machine can't test it (G6d on 1–2 cores, where the 5 s clock always comes before the 10 s CPU limit), or inconclusive, when it didn't run as intended, for example because the judge failed. The make target passes only if every probe is contained or skipped. Since sandboxing step 4, the first 13 are contained here and on Kubuntu; on the 2-core VPS, G6d is skipped. The 14th, G11 (added 2026-11-02 for step 6), makes four system calls the seccomp filter must refuse, and has been contained since that filter was added. It needs no server and no npm install, only the toolchains.
make deploy-serverFor the VPS: does docs/deploy-vps.md §1–§6 and §8 in one go (“The quick way” there). It runs toolchain-deps and sandbox-deps with systemd's own PATH, then scripts/deploy-server.sh, which creates the maxrecall user, clones master into /srv/maxrecall/maxrecall-dsa.net, runs npm install, and installs, enables and starts the service. It then fails if the service's Sandbox: line says UNAVAILABLE or its ports listen beyond 127.0.0.1. Run again, it updates. Needs root (asks for sudo), and the first run asks before changing anything (DEPLOY_CONFIRM=yes skips that). Not for your desktop: the trusted port makes anyone on the machine the owner.
make open-ssh-3005On Kubuntu: opens the SSH tunnel to the VPS's trusted port (ssh -N -L 3005:127.0.0.1:3001 root@$(VPS_HOST), docs/deploy-vps.md §7). Then browse http://localhost:3005; Ctrl-C closes it. Port 3005 avoids make dev's 3000. VPS_HOST defaults to the VPS's hostname; override it with make open-ssh-3005 VPS_HOST=…. Added by the owner on 2026-11-02.
make cleanDeletes node_modules.

Both open http://localhost:3000/ for you. There is no compile step for the front end: it's plain HTML/CSS/JS. Source: Makefile, package.json.

You have to sign in (see the API section's sign-in gate), and Submits are saved for whoever is signed in. MAXRECALL_USER (default daniel.pflager@gmail.com) is the owner: the only email allowed to register. The server won't start if it isn't a plain email address, and it prints whether registration is open when it starts.

TRUSTED_PORT (unset by default; 3001 on the VPS) opens a second listener on 127.0.0.1 only, where every request is the owner, MAXRECALL_USER, with no sign-in. It's for the VPS's SSH tunnel, and it's a separate port, not "trust requests from 127.0.0.1", because a reverse proxy on the same machine would make every visitor look like 127.0.0.1. The server won't start if it isn't a valid port different from PORT.

Settings can go in a .env file in the repo (gitignored; copy .env.example). It's read at startup with Node's process.loadEnvFile, and anything already set in the environment wins over it. MAXRECALL_PASSWORD is the fixed password that registering requires (at least 10 characters, or the server won't start; empty means registration is closed). MAXRECALL_AUTH_DIR moves account and session data out of the repo's gitignored auth/.

The server listens on every network interface unless the HOST environment variable says otherwise. With HOST=127.0.0.1 it accepts connections only from the same machine, which is how it runs on the VPS behind an SSH tunnel (see Environments). The first line it prints says which. MAXRECALL_USERS_DIR moves saved submissions out of the repo's users/ (see Where data lives). Source: server.js, users.js.

At startup the server checks that the judge's sandbox, bubblewrap, works, and prints a Sandbox: line saying so. If it doesn't, Run and Submit are refused with HTTP 503 and the reason, unless MAXRECALL_UNSANDBOXED=1 is set, which allows judging without a sandbox (for setting up your own machine, never a shared server). make run and make dev install what's missing first (make sandbox-deps, above). Source: judge/sandbox.js.

Make variables given on the command line (PORT=8080) override the PORT ?= 3000 default — see the GNU Make manual, “Overriding Variables”.

4. HTTP API

Method & pathBehaviour
POST /api/auth/registerBody {email, password}. Succeeds only for MAXRECALL_USER with exactly MAXRECALL_PASSWORD, and only once; any refusal is 400 with one generic message. On success, sets the session cookie and returns {email}.
POST /api/auth/loginBody {email, password}. 401 with "Invalid email or password." for any failure. After 5 failures for an email, 429 with Retry-After until the wait (doubling, up to 15 minutes) is over. On success, ends any session the browser had and sets a new cookie.
POST /api/auth/logoutEnds the session and clears the cookie.
GET /api/auth/me{email, trusted} if signed in (trusted is true on the trusted port), otherwise 401.
GET /api/questionsList of {slug, title, difficulty, topics, sources}, sorted by title.
GET /api/questions/:slugThe problem with hidden test cases removed: visibleTestCases plus a hiddenCount.
POST /api/questions/:slug/runBody {language, code}. Judges against visible test cases only.
POST /api/questions/:slug/submitSame body. Judges against all test cases, hidden included, then saves a record (see Where data lives). The response adds saved: true and submissionId (the record's timestamp), or saved: false and saveError if the save failed. The judged result is returned either way, and the page shows a “not saved” warning.
GET /api/submissionsThe current user's saved Submits, newest first, as summaries: {id, submittedAt, question, language, status, passed, total, runtimeMs} (no code, stdout or stderr). ?question=<slug> and ?language=<language> narrow it down; giving either twice, or an unknown language, is a 400. The problem page always asks for one question in one language. Unreadable files are skipped with a warning in the server log.
GET /api/submissions/:idOne saved Submit in full, including code, stdout and stderr. :id is the file's timestamp, e.g. 2026-10-29T04-05-29.199Z, and must match that pattern exactly; otherwise, or if there's no such file, 404.
(all of the above)Sign-in gate: without a valid session cookie, every URL except /login.html, /login-page.js, /style.css and the login/register endpoints is refused: pages redirect to /login.html?next=…, API calls get 401. Every POST to /api/ must be JSON, or it's 415. A form on another site can't send JSON without a CORS preflight, which the server never approves, so this and SameSite=Lax are the cross-site request forgery defence. The cookie is maxrecall_session: HttpOnly, SameSite=Lax, Path=/, 360 days, and Secure when the request came over HTTPS.
any other /api/…404 with {error} JSON. The API was at /api/problems/… until 2026-10-29.
GET /<file>Only the files in the STATIC_FILES list are served; anything else falls back to index.html.

Source: server.js.

6. Judging

Modes

  • function: the learner writes one function. The runner wraps it in generated boilerplate that calls it once per test case inside one process, then compares return values to expected with a deep-equality check.
  • program: the learner writes a whole program that reads stdin and writes stdout. Each test case is a separate process. Output is compared after trimming leading/trailing whitespace.

Languages, toolchains and limits

LanguageToolchain invokedMemory capHow the cap is applied
JavaScriptnode128 MB--max-old-space-size (V8 heap only)
Pythonpython3256 MBRLIMIT_AS via resource.setrlimit or ulimit -v
C++g++ -std=c++17 -O2128 MBulimit -v
Javajavac / java256 MB-Xmx (heap only)
Dldc2 (LDC) if installed, else dmd128 MBulimit -v

Every run is killed with SIGKILL after 5 s; compiling gets 10 s. In program mode, where each test case is its own run, all of a submission's runs together may take at most 20 s (PROGRAM_TOTAL_RUN_MS, not counting compiling). A case is cut short if less than 5 s is left, and cases still waiting when the time is used up aren't run; both count as Time Limit Exceeded. Compilers and submissions get only PATH and LANG=C.UTF-8 as their environment, not a copy of the server's (SUBMISSION_ENV, in judge/sandbox.js). LANG makes Java print UTF-8, which it otherwise doesn't in the cloud. runSubmission refuses to judge if the sandbox failed its startup check (see Running it).

Compiling and running are sandboxed with bubblewrap (since 2026-11-02, sandboxing steps 3 and 4). Each submission gets its own folder (/tmp/judge-XXXXXX, owner-only, deleted afterwards). The compiler sees it as /work, writable, so it can write the binary or classes. The run sees it read-only as /work: main.js, main.py, Main.java and its classes, or the binary main. The judge's helpers are read-only at /judge/java and /judge/cpp/judge_json.o. They're copies, made at startup in a /tmp/judge-helpers-<pid>-XXXXXX folder that's removed on exit, or at the next start if the server was killed by a signal, not binds from the checkout, so the checkout can live where the sandbox's user can't go, such as /root. Compilers get a memory cap too: 1 GB of address space for g++ (with its cc1plus, as and ld) and the D compiler, and a 256 MB heap for javac (-J-Xmx256m, because a JVM reserves more address space than it uses). A compile that runs out reports “virtual memory exhausted” as a Compile Error. So error messages show paths such as /work/main.py. Inside the sandbox there's:

  • a read-only /usr and the few /etc files the toolchains need;
  • a private 64 MB /tmp;
  • no network but its own loopback;
  • its own process list, an empty environment apart from PATH and LANG, and no capabilities;
  • a seccomp filter (since 2026-11-02, sandboxing step 6) that refuses about 50 system calls with EPERM. They're kernel interfaces a judged program never needs and that have a history of security bugs: bpf, io_uring_*, userfaultfd, keyctl, ptrace, mounts and namespaces, kernel modules and others (SECCOMP_DENYLIST). It also makes clone3 fail with ENOSYS, so the C library falls back to clone, and refuses clone with namespace flags. Calls from another processor architecture (including x86-64's 32-bit-pointer x32 calls) kill the process. The server builds it at startup from judge/seccomp/gen.cpp with libseccomp, and bubblewrap installs it in each sandbox (--seccomp).

Limits are set with prlimit inside the sandbox (RUN_LIMITS): 128 processes and threads, 16 MB per file, no core dumps, and 10 s of CPU time per process (all its threads together; SIGKILL at 11 s). The CPU limit is a backstop to the 5 s wall-clock timeout, which on its own allows 5 s × cores of CPU. A run it stops is reported as Time Limit Exceeded with “CPU time limit exceeded”. The judge recognises it by bwrap's exit code 152, which is 128 + SIGXCPU. They're inside because the process count is per user namespace there; set outside, it would count every process the server's user owns. Killing a run on timeout kills everything in its sandbox. When the server runs as root (the cloud), sandboxes run as nobody, because root ignores the process limit. make sandbox-test checks all of this.

Captured stdout/stderr is capped at 200,000 characters. The user's own prints are separated from the harness's result by a ###JUDGE_RESULT### marker line. Source: judge/runner.js (constants at the top, runCommand, spawnJudged, runFunctionSubmission, runProgramSubmission) and judge/sandbox.js (BASE_ARGS, RUN_LIMITS, sandboxedRun).

7. Front end

  • Editor: CodeMirror 5.65.16; math: KaTeX 0.16.9. Both are loaded from cdnjs, so the problem page needs internet access to render properly.
  • The browser keeps each language's code and console output in memory while you switch languages on one page. A reload loses them.
  • Preferences are kept in the browser's localStorage under these keys: maxrecall-dsa:description-pane-width, maxrecall-dsa:default-language, maxrecall-dsa:available-languages.
  • The Skip button is a placeholder that only shows an alert.
  • Which tab you see, per language: when a question opens, or you switch its language (dropdown, language menu), you see Learning if you have no saved Submit for it in that language, and Applying if you have, to encourage answering it. A question with no Learning text for that language shows Applying. Reopening a submission from the page address shows Applying, in that submission's language. Submitting doesn't move you, and you can switch tabs freely. If your submissions can't be loaded, you see Learning. Source: problem-page.js, showLanguage.
  • Every page needs you to be signed in (see the API section's sign-in gate). The header shows your email and a Log out button (account.js). On the trusted port there's no sign-in, and a yellow “trusted (SSH tunnel)” marker shows instead of the button.
  • The Submissions tab lists your saved Submits for this question in the current language only, newest first (local time, verdict, tests passed, run time), and changes with the language, from GET /api/submissions?question=. It refreshes after each saved Submit. Load switches to that submission's language and puts its code in the editor. It asks first only if that language's code has been edited, and explains if the language is turned off in the language menu. Loading switches the editor's language but, unlike the dropdown, doesn't change your default language. It also adds &submission=<id> to the page address (history.replaceState, no reload), so reloading or bookmarking reopens that submission's language and code; edits made since are not kept. A saved Submit puts its own id there, so a reload reopens what was just submitted (Run, or a Submit that failed to save, leaves the address alone). Choosing a language yourself (dropdown or language menu) removes it from the address. If the address names a submission that's missing, belongs to another question, or is in a language that's turned off, the page opens normally, drops it from the address, and the Submissions tab says why.
  • The problem page header shows the difficulty, then the question's sources as outlined bubbles, then its topics as filled bubbles, each in file order, coloured from labels.json. The problem list shows the same bubbles in its “Sources & topics” column.

Source: problem.html, problem-page.js, index.html, problems-list.js, bubbles.js.

8. Where data lives

Every Submit is saved; Run is not. Each Submit writes one file:

users/<email>/submissions/<timestamp>.json

users/ is in the repo unless the MAXRECALL_USERS_DIR environment variable points elsewhere. The VPS uses /srv/maxrecall/data/users, outside its checkout, so git pull there never collides with its records. The server's first log line says which folder it's using.

All questions share that one folder; each record's question field says which question it was.

<email> is the signed-in user's email, lower-cased, taken from their session for each request, and checked against a strict pattern again before it's used in a path. <timestamp> is the UTC submit time with : replaced by -, e.g. 2026-10-29T03-27-46.194Z, so files sort by time. The file is written under a temporary name and then hard-linked into place with link(), so a crash never leaves half a record. Unlike rename(), link() refuses to replace an existing file, so two Submits in the same millisecond (from two tabs) produce a “not saved” warning rather than one overwriting the other.

FieldMeaning
schemaVersion1. Bump it if the format changes.
submittedAtUTC ISO-8601 time the Submit arrived.
question, questionSha256The question's slug, and the SHA-256 of questions/<slug>.json as it was then, to show whether the question has been edited since.
language, judgeMode, codeWhat was submitted, and how it was judged.
status, passed, total, runtimeMsThe judge's verdict, as shown in the Results tab.
resultsPass/fail for each test case, in file order.
stdout, stderrThe program's output.

Accounts and sessions are kept in auth/ (or MAXRECALL_AUTH_DIR), which is gitignored and created with owner-only permissions:

  • accounts/<email>.json: the email, the scrypt parameters (N=217, r=8, p=1, the OWASP minimum), a random salt and the hash. Never the password.
  • sessions/<sha256 of token>.json: the email and the expiry time (360 days after login). The browser holds the random 256-bit token; the server keeps only its hash, so reading this folder doesn't give anyone a usable token.

Failed-attempt counts for throttling are kept in memory only, so restarting the server clears them. Source: auth.js.

users/ is gitignored (since 2026-10-30): submissions stay on the machine that recorded them, and the owner manages that folder by hand. nodemon ignores users/, so saving doesn't restart make dev. The other persistent state is the browser preferences above, which belong to one browser on one machine. Source: users.js, server.js (handleExecution, /api/submissions).

The VPS (third place, from 2026-10-29)

A Hostinger VPS running Ubuntu 24.04 can run the app for testing, set up by docs/deploy-vps.md. It uses Node 22 from nodejs.org (Ubuntu's own package is 18.19), g++ 13.2 and OpenJDK 21 from Ubuntu, and no D compiler. The server listens only on 127.0.0.1: port 3000 needs sign-in, and the trusted port 3001 makes you the owner with no sign-in. You reach the trusted port with ssh -N -L 3000:127.0.0.1:3001 root@VPS_IP. Accounts and sessions live in /srv/maxrecall/data/auth. An optional root-only /etc/maxrecall-dsa/test.env holds MAXRECALL_PASSWORD, needed only to register on port 3000. It runs as the maxrecall user under systemd containment: no network except loopback, and a read-only file system apart from its data and the judge's helper folders. Its submissions are copied to Kubuntu with rsync and committed there. That containment is now an outer layer around the judge's own sandbox (see Judging). 10. Known gaps & caveats

Submitted code is sandboxed, but not fully hardened yet (docs/plans/sandboxing.md). Since step 4, compiling and running are both inside bubblewrap (see Judging), and make sandbox-test reports all 13 probes contained. Step 4 closed three gaps: compilers reading host files (#include, G7); the C++ compile timeout leaving cc1plus running (G10, measured at 137 s with a 1 s timeout before the fix); and compilers with no memory limit (a 257-byte template source went from 2 GB and growing to a Compile Error after 6.6 s). What's still open:

  • No cgroup limits (step 7). Memory is capped per language, as before, and the 64 MB /tmp is kernel memory. The CPU limit is per process, so a submission that forks gets 10 s of CPU per process.
  • The reported runtime includes compiling and sandbox start-up, because runtimeMs is measured from before the compile.
  • No limit on concurrent judgings (step 8).
  • The kernel is shared with the host, as with any namespace sandbox.

That's fine for the owner alone, and it's the remaining work before others are let in. Source: judge/runner.js, judge/sandbox.js.

Found while planning the fix on 2026-11-02 (docs/plans/sandboxing.md §1): submissions inherited the server's whole environment, including MAXRECALL_PASSWORD (spawn passes process.env on by default). Since sandboxing step 1 they get only PATH and LANG, but they can still read the server's starting environment from /proc/<pid>/environ. That includes a password the VPS gets from EnvironmentFile=, though not one read from .env at runtime. They could also read questions/*.json, so hidden test cases' expected answers too; and a process a submission forked outlived the timeout. A Python submission that forked and called setsid() kept running after the judge gave up, and the judge reported 8042 ms instead of 5000, because the orphan held the output pipe open. Step 3 closed all three for runs (probes G1, G2, G5a and G5b contained).

  • package-lock.json is gitignored, so the cloud and Kubuntu can install different dependency versions. npm's docs say it's meant to be committed.
  • There are no automated tests yet, apart from the judge's escape test (make sandbox-test), which is a security check rather than a test of features.
  • Sign-in limits: no password reset or change (with one user, delete auth/accounts/<email>.json and register again); throttling is in memory, so a restart clears it; if a session expires while a page is open, its requests fail with "Not signed in" instead of going back to the login page; and behind a future HTTPS reverse proxy, Express's trust proxy setting will be needed for req.secure, and so the cookie's Secure flag, to work.
  • The cloud environment has no D compiler of its own. The SessionStart hook installs LDC from Ubuntu's archive (scripts/toolchain-deps.sh). If that fails, the hook reports an error (the session still starts) and D submissions fail in that session. Until 2026-11-02 it installed DMD from d-apt on SourceForge instead, since dlang.org's downloads are blocked by the cloud's network policy.
  • The problem page needs internet access. problem.html loads CodeMirror 5.65.16 and KaTeX 0.16.9 from cdnjs.cloudflare.com. Without them (offline, or where the CDN is blocked, as in the cloud sandbox), CodeMirror is undefined. init() then throws when loadLanguage creates the editor (problem-page.js line 512), before it wires up Run/Submit/Skip (line 687), so those buttons do nothing. KaTeX alone is optional: renderMath checks for it and leaves the math as plain text. The problem list (index.html) uses no CDN. A fix would be to install both with npm and serve them locally. Found 2026-10-29. Source: problem.html, problem-page.js.

12. Maintaining this file

This page only helps if it's kept true. Update it in the same commit as the change that makes it out of date. That includes:

  • adding, removing or renaming a file or directory → Layout;
  • adding or changing an endpoint → API;
  • a new or changed field in problem files → Problem file format;
  • a new language, toolchain, limit or judging rule → Judging;
  • a new localStorage key, CDN library or page → Front end;
  • anything stored on disk or in a database → Where data lives;
  • a toolchain installed or upgraded on either machine → Environments;
  • a gap fixed or found → Known gaps;
  • a design decision made, or a plan started or finished → Decisions & plans.

Conventions:

  • State only what the code actually does. Where a fact comes from code, name the file in a Source: line so it can be checked.
  • Mark anything unverified as a guess.
  • Bump “Last updated” at the top.
  • Keep the page self-contained: no external CSS, JS or fonts.
