1. Purpose

A learning-first practice system for data structures and algorithms, taking the best from sites like LeetCode and HackerRank but focused on teaching rather than testing: a learner should get direct instruction (the Learning tab) before being asked to solve something. It is meant to grow into a multi-user, web-hosted system. Source: THOUGHTS, TODO.

2. Running it

CommandWhat it does
make toolchain-depsRuns scripts/toolchain-deps.sh, which every target that needs Node runs first (install, run, dev, sandbox-test). It installs what docs/deploy-vps.md §1–§2 list, plus LDC for D, if it's missing:
  • g++, default-jdk-headless, python3, ldc, curl and xz-utils from apt;
  • Node 22.23.4 from nodejs.org into /usr/local, checked against nodejs.org's SHASUMS256.txt and the hash recorded in the script, but only if the node your PATH finds first is older than 22 (Node 20 reached end-of-life in April 2026).
It uses sudo only when it has something to install. Unlike sandbox-deps, it stops make if it can't fix things, because the server can't start without these. One case it can't fix: an older node still first on your PATH. It says which one and where to look. It also warns, without stopping, about a node that's an odd-numbered release (never LTS), past its end of life, or within 90 days of it, using end dates copied from the Node.js Release team's schedule.json (read 2026-11-02). Node 22, which the VPS uses, ends on 2027-04-30, so the warning starts in February 2027 (issue #25).
make installRuns npm install if node_modules is older than package.json.
make sandbox-depsRuns scripts/sandbox-deps.sh, which make run and make dev also run first. It checks that the judge's sandbox works (about 0.1 s, no root). If it doesn't, it fixes what it can, using sudo, which may ask for your password, and saying what it runs. It installs bubblewrap if missing, and libseccomp-dev, which the server needs to build the sandbox's seccomp filter. If Ubuntu's AppArmor restriction on user namespaces is what stops bubblewrap, it installs apparmor-profiles and loads Ubuntu's bwrap-userns-restrict profile. That's a machine-wide change, made only in that case: afterwards any user's bwrap may create user namespaces. If it can't fix things, it warns and lets the server start, and the server then refuses to judge. Run as root, it checks as nobody, like the server does when it's root, because root may create user namespaces even where AppArmor blocks everyone else. Until 2026-11-02 its second check ran as root, so on the VPS it blamed something other than AppArmor and didn't load the profile.
make runStarts the server in the foreground (PORT=3000 node server.js; Ctrl-C stops it). In the background it polls the server with curl every 0.2 s until it answers, then opens it with xdg-open (your default browser). If the server hasn't answered within about OPEN_WAIT seconds (±1 s) (default 30; e.g. make run OPEN_WAIT=60), it prints a message and gives up on the browser. Override the port with make run PORT=8080. Needs curl and xdg-open (package xdg-utils); the cloud environment has no xdg-open, so there the browser step fails and the server still runs.
make devStarts the server under nodemon, which restarts it whenever a .js, .mjs, .cjs or .json file changes, except under users/ (set in package.json → nodemonConfig). Opens the browser once at startup, the same way as make run; restarts don't open it again.
make testRuns the unit tests: every *.test.js in the top folder (so far advance.test.js, introduce.test.js, questions.test.js, profile.test.js, order.test.js, consistency.test.js, recalculate.test.js, users.test.js, learner.test.js, playtest.test.js, auth.test.js and routes.test.js), with Node's built-in test runner (node --test), in about 4.5 s after toolchain-deps (measured in the cloud, 2026-11-06; the files run side by side): routes.test.js takes about 4 s, and auth.test.js about 2 s, because each registration hashes with scrypt. None needs the sandbox. routes.test.js starts node server.js and judges Python and JavaScript, so it needs python3 and node (toolchain-deps); with MAXRECALL_UNSANDBOXED=1 it judges without the sandbox where it doesn't work, and inside it where it does. The files are named in the Makefile rather than left to node --test's default patterns, which would also pick up judge/line-numbers-test.js (it matches *-test.js).
make doc-checkChecks that every function in the files tsconfig.json and tsconfig.browser.json list has a JSDoc block documenting its signature: a @param for each parameter and a @returns (constructors and setters excepted), as CLAUDE.md requires. make typecheck checks that the types written are right; this checks that they're written at all. Exempt, as the owner decided: single-expression arrows, empty no-ops like .catch(() => {}), and test bodies (a function passed straight to test(...) in a *.test.js). Fails, listing each function as file:line, if any isn't documented. Uses TypeScript 6.0.3's parser, the typescript6 development dependency (an npm alias, npm:typescript@6.0.3), because TypeScript 7's package has no JavaScript API. Source: scripts/doc-check.js.
make consistency-checkThe consistency check (spaced-repetition plan, D5, step 10): compares questions/ and questions/renames.json with every user's profile.json, order.json, backlog.json and Submit and Skip records, and lists what disagrees, grouped by user, as error (an invalid file: the server already refuses that user's Run and Submit), warning (a deleted or renamed question, a question that lost a language, a pair in neither file, a queue result the records don't bear out, a backlog pair with records, an unreadable record) or info (a language the profile no longer allows, kept on purpose). Pairs submitted before the queue existed are one summary line per user; VERBOSE=1 lists each. Only reads, so it's safe while the server runs, though a Submit landing mid-check can show a pair in neither file for a moment. Uses MAXRECALL_USERS_DIR like the server. Fails (make's “Error 1”) only for an error. The server runs the same check once at start (see Where data lives).
make delete-question SLUG=…, make rename-question FROM=… TO=…Deleting and renaming a question (spaced-repetition plan, D5, step 11). Delete: git rm questions/SLUG.json, then every user's order.json and backlog.json lose it. Rename: git mv to TO.json, its slug line changed, {"FROM": "TO"} added to questions/renames.json (kept so every value is a current name; renaming back removes the old entry), then every user's references renamed, keeping their place and progress; if the pair ends up twice, the backlog copy goes (or, in the queue under both names, the old-name one). The git changes are staged, not committed: each ends by printing the git commit to run. If the file change already happened (a git pull on the VPS: see docs/deploy-vps.md §8), only the references are updated. Both refuse, changing nothing, for an invalid name (lowercase letters, digits, single hyphens), a TO that exists, a FROM that neither exists nor is recorded as renamed to TO, deleting an old name, any user's invalid queue files, or a server answering on 127.0.0.1:$PORT (default 3000) or $TRUSTED_PORT: stop the server first. DRY_RUN=1 prints what would change and changes nothing. Submit and Skip records are never changed. The names reach the script through its environment, never pasted into the recipe, so a name can't run as shell code.
make recalculate-queue EMAIL=…Recalculates one learner's order.json and backlog.json from their Submit and Skip records (spaced-repetition plan, step 12a): starting as a new user does, every record, oldest first, goes through the same rule a Submit uses, so the result is the queue they'd have had if spaced repetition had existed from their first Submit, and make consistency-check then finds nothing to do with check 6. Old names are followed through renames.json; records of deleted questions are left out; records in a language turned off or no longer allowed are replayed too (kept, and passed over while off). The random number generator is seeded from the email, so DRY_RUN=1 shows exactly what will be written, and running it twice gives the same files. It shows the first 10 pairs of the queue before and after. Before writing, it keeps a copy of both files beside them, <name>.before-recalculate-<UTC time>, to go back to by copying them over. It refuses, changing nothing, for an unknown EMAIL, an invalid profile or renames.json, a record that can't be read, or a server answering on 127.0.0.1:$PORT: stop the server first. With a chosen backlog (step 13) it starts from the pairs chosen, every pair in the two files now (the queue's, in queue order, then the backlog's), instead of every allowed pair, and refuses if those files are invalid, since the choice is read from them.
make invite EMAIL=…Makes an invite code for one email and prints it (scripts/invite.js; limited live plan, D2). With it, that email can register once, within 7 days, with a password of its own; a new invite for the same email replaces the old one. Run it as the user who owns the sign-in folder, or it refuses: on the VPS, sudo -u maxrecall env MAXRECALL_AUTH_DIR=/srv/maxrecall/data/auth make invite EMAIL=…. The server can keep running.
make backlog-show EMAIL=…, make backlog-add EMAIL=… SLUGS="…" [AT=n], make backlog-remove EMAIL=… SLUGS="…"Choosing a learner's backlog (spaced-repetition plan, step 13), for a profile.json with "backlog": "chosen", where the server adds nothing to the backlog by itself. Show lists the learner's settings, queue and backlog, then every question, oldest first, with where each of its pairs in a language turned on is (queue 1, backlog 2 or not chosen); it only reads. Add adds the questions in SLUGS (names separated by spaces), in that order, each in every language turned on that it has, in the learner's order, at the end of the backlog or from position AT (1 is the front, the next to come in). A pair already in the queue or the backlog isn't added again, and is listed as not added; to move one, remove it and add it again. Remove takes the questions out of the backlog in every language; one already in the queue stays there. Both write backlog.json only, and refuse, changing nothing, for an unknown EMAIL, a profile without "backlog": "chosen", an invalid profile or queue file, an unknown question (add), an AT outside 1 to one more than the backlog's length, or a server answering on 127.0.0.1:$PORT: stop the server first. DRY_RUN=1 shows the backlog after and changes nothing. A pair added comes into the queue at the learner's next Submit or Skip (recordSubmit), not at once. Source: scripts/backlog.js, order.js.
make learner-create EMAIL=… LANGUAGES=… SLUGS="…"Sets up a new learner before their invite goes out (spaced-repetition plan, step 14; limited-live Q3, option (c)): writes users/<email>/, the email lower-cased as registering makes it, with profile.json (allowed.languages from LANGUAGES, the first being their default, and "backlog": "chosen"), an empty order.json, and backlog.json holding SLUGS in that order, each in every one of those languages it has. All three appear at once: they're written into a temporary folder, users/.new-user-<random> (no @, so never taken for a user), which is then renamed into place. It refuses, changing nothing, for an email this app doesn't accept, a missing or unknown language or question, or a folder that already exists: it never replaces anyone (make backlog-add and backlog-remove change an existing learner). The server can keep running: nothing else writes the folder of someone with no account yet, and the server reads a learner's files at each request. It doesn't make the invite; it prints the make invite command. DRY_RUN=1 shows the files and writes nothing. Procedure: docs/deploy-vps.md §11. Source: scripts/learner-create.js, learner.js, users.js (createUser).
make typecheckChecks the JSDoc types (@param, @returns, @type) with TypeScript's checker, twice: the Node files tsconfig.json lists (advance.js, advance.test.js, introduce.js, introduce.test.js, questions.test.js, profile.js, profile.test.js, order.js, order.test.js, question-files.js, consistency.js, consistency.test.js, recalculate.js, recalculate.test.js, paths.js, users.js, users.test.js, learner.js, learner.test.js, playtest.js, playtest.test.js, auth.js, auth.test.js, server.js, routes.js, the judge's six judge/*.js, and scripts/doc-check.js, scripts/consistency-check.js, scripts/question-admin.js, scripts/recalculate-queue.js, scripts/backlog.js, scripts/learner-create.js and scripts/invite.js), then the browser files tsconfig.browser.json lists (all six: problem-page.js, login-page.js, problems-list.js, bubbles.js, timer.js, account.js), which need the DOM's types instead of Node's. Nothing is compiled. Since 2026-11-03 every JavaScript file in the repository is in one of the two, except, for now, routes.test.js and scripts/characterize.js (2026-11-06): both are documented, and both checks pass with them listed, but tsconfig.json is infrastructure and security's, asked to add them. A new file goes in once its functions are documented (CLAUDE.md, docs/plans/documentation-standard.md). Checking a file also checks every file it requires. TypeScript 7.0.2, @types/node 22.20.5, @types/express 4.17.25 and @types/codemirror 5.60.18 (for the editor, CodeMirror 5.65.16) are development dependencies, pinned exactly because package-lock.json is gitignored (a new TypeScript can report new errors). Runs npm install first if package.json changed. Write a function type as {() => number}: TypeScript 7 rejects the older {function(): number} with “'}' expected” (found 2026-11-03; 6.0.3 accepted both).
make line-numbers-testRuns judge/line-numbers-test.js (about a minute). It submits a mistake on line 3 in each language, in both judging modes, checks that the judge's message names line 3 of the right file, and checks that a runtime error on line 3 ends in “(line 3)” (your own mistake, and an exception thrown by a library you called), and that correct answers to two-sum and the linked-list question are still Accepted in all five languages, plus a few edge cases. 36 checks; it fails if any does.
make sandbox-testRuns judge/sandbox-selftest.js, the judge's escape test (about 30 s). Each probe is a hostile submission, and the result says whether it was contained or ESCAPED. A probe can also say skipped, when this machine can't test it (G6d on 1–2 cores, where the 5 s clock always comes before the 10 s CPU limit), or inconclusive, when it didn't run as intended, for example because the judge failed. The make target passes only if every probe is contained or skipped. Since sandboxing step 4, the first 13 are contained here and on Kubuntu; on the 2-core VPS, G6d is skipped. The 14th, G11 (added 2026-11-02 for step 6), makes four system calls the seccomp filter must refuse, and has been contained since that filter was added. The 15th, G12 (step 7), uses more memory in several processes together than a submission's cgroup allows; it's skipped where cgroups aren't in use. The 16th, G9 (step 8), starts 20 judgings at once and counts, from /proc, how many really run together. It needs no server and no npm install, only the toolchains.
make deploy-serverFor the VPS: does docs/deploy-vps.md §1–§6 and §8 in one go (“The quick way” there). It runs toolchain-deps and sandbox-deps with systemd's own PATH, then scripts/deploy-server.sh, which creates the maxrecall user, clones master into /srv/maxrecall/maxrecall-dsa.net, runs npm install, and installs, enables and starts the service. It then fails if the service's Sandbox: line says UNAVAILABLE or its ports listen beyond 127.0.0.1. Run again, it updates. Needs root (asks for sudo), and the first run asks before changing anything (DEPLOY_CONFIRM=yes skips that). Not for your desktop: the trusted port makes anyone on the machine the owner.
make open-ssh-3005On Kubuntu: opens the SSH tunnel to the VPS's trusted port (ssh -N -L 3005:127.0.0.1:3001 root@$(VPS_HOST), docs/deploy-vps.md §7). Then browse http://localhost:3005; Ctrl-C closes it. Port 3005 avoids make dev's 3000. VPS_HOST defaults to the VPS's hostname; override it with make open-ssh-3005 VPS_HOST=…. Added by the owner on 2026-11-02.
make cleanDeletes node_modules.

Both open http://localhost:3000/ for you. There is no compile step for the front end: it's plain HTML/CSS/JS. Source: Makefile, package.json.

You have to sign in (see the API section's sign-in gate), and Submits are saved for whoever is signed in. MAXRECALL_USER (default daniel.pflager@gmail.com) is the owner: who you are on the trusted port (below). The server won't start if it isn't a plain email address. Anyone, the owner included, registers with an invite code from make invite (since 2026-11-04; below).

TRUSTED_PORT (unset by default; 3001 on the VPS) opens a second listener on 127.0.0.1 only, where every request is the owner, MAXRECALL_USER, with no sign-in. It's for the VPS's SSH tunnel, and it's a separate port, not "trust requests from 127.0.0.1", because a reverse proxy on the same machine would make every visitor look like 127.0.0.1. The server won't start if it isn't a valid port different from PORT.

Settings can go in a .env file in the repo (gitignored; copy .env.example). It's read at startup with Node's process.loadEnvFile, and anything already set in the environment wins over it. MAXRECALL_AUTH_DIR moves account, session and invite data out of the repo's gitignored auth/. MAXRECALL_PASSWORD, the fixed password registering needed until 2026-11-04, is no longer used; the server says so at startup if it's still set.

The server listens on every network interface unless the HOST environment variable says otherwise. With HOST=127.0.0.1 it accepts connections only from the same machine, which is how it runs on the VPS behind an SSH tunnel (see Environments). The first line it prints says which. MAXRECALL_USERS_DIR moves saved submissions out of the repo's users/ (see Where data lives). Source: server.js, users.js.

At startup the server checks that the judge's sandbox, bubblewrap, works, and prints a Sandbox: line saying so. If it doesn't, Run and Submit are refused with HTTP 503 and the reason, unless MAXRECALL_UNSANDBOXED=1 is set, which allows judging without a sandbox (for setting up your own machine, never a shared server). make run and make dev install what's missing first (make sandbox-deps, above). Source: judge/sandbox.js.

Make variables given on the command line (PORT=8080) override the PORT ?= 3000 default — see the GNU Make manual, “Overriding Variables”.

6. Judging

Modes

  • function: the learner writes one function. The runner wraps it in generated boilerplate that calls it once per test case inside one process, then compares return values to expected with a deep-equality check.
  • program: the learner writes a whole program that reads stdin and writes stdout. Each test case is a separate process. Output is compared after trimming leading/trailing whitespace.

Languages, toolchains and limits

LanguageToolchain invokedMemory capHow the cap is applied
JavaScriptnode128 MB--max-old-space-size (V8 heap only)
Pythonpython3256 MBRLIMIT_AS via resource.setrlimit or ulimit -v

Every run is killed with SIGKILL after 5 s; compiling gets 10 s. In program mode, where each test case is its own run, all of a submission's runs together may take at most 20 s (PROGRAM_TOTAL_RUN_MS, not counting compiling). A case is cut short if less than 5 s is left, and cases still waiting when the time is used up aren't run; both count as Time Limit Exceeded. Compilers and submissions get only PATH and LANG=C.UTF-8 as their environment, not a copy of the server's (SUBMISSION_ENV, in judge/sandbox.js). LANG makes Java print UTF-8, which it otherwise doesn't in the cloud. runSubmission refuses to judge if the sandbox failed its startup check (see Running it).

Compiling and running are sandboxed with bubblewrap (since 2026-11-02, sandboxing steps 3 and 4). Each submission gets its own folder (/tmp/judge-XXXXXX, owner-only, deleted afterwards). The compiler sees it as /work, writable, so it can write the binary or classes. The run sees it read-only as /work: main.js, main.py, Main.java and its classes, or the binary main. In function judging, the learner's code is a file of its own next to the harness, so messages give the line numbers the editor shows (issue #26): solution.py, run by the harness with runpy.run_path (given sys and json, as __main__); solution.cpp, #included after the harness's includes; Solution.java, compiled with Main.java; and solution.d, a module of its own compiled with main.d, which imports it and calls the function as solution.<name>. solution.d starts with import judge_prelude; on its first line (so no line moves), and judge_prelude.d public imports the harness's 10 standard modules. So the code still sees the harness's imports and includes, as it did when it was pasted in. When the harness catches an exception from a test case, the message ends in “(line N)”, the deepest line of the learner's code on its stack, so an exception thrown inside a library points at the learner's call: traceback.extract_tb (Python), the at …main.js:N frames within the learner's lines (JavaScript), getStackTrace() (Java), and Throwable.file/line or the stack trace (D, which function judging compiles with -g for that: about 200 ms more per D judging, measured in the cloud). Not C++, whose exceptions carry no location. An empty Python message becomes the exception's type name. JavaScript's harness follows the learner's code in main.js, which already numbered lines right. Program judging writes the code as the only file. The judge's helpers are read-only at /judge/java and /judge/cpp/judge_json.o. They're copies, made at startup in a /tmp/judge-helpers-<pid>-XXXXXX folder that's removed on exit, or at the next start if the server was killed by a signal, not binds from the checkout, so the checkout can live where the sandbox's user can't go, such as /root. Compilers get a memory cap too: 1 GB of address space for g++ (with its cc1plus, as and ld) and the D compiler, and a 256 MB heap for javac (-J-Xmx256m, because a JVM reserves more address space than it uses). A compile that runs out reports “virtual memory exhausted” as a Compile Error. So error messages show paths such as /work/main.py. Inside the sandbox there's:

  • a read-only /usr and the few /etc files the toolchains need;
  • a private 64 MB /tmp;
  • no network but its own loopback;
  • its own process list, an empty environment apart from PATH and LANG, and no capabilities;
  • a seccomp filter (since 2026-11-02, sandboxing step 6) that refuses about 50 system calls with EPERM. They're kernel interfaces a judged program never needs and that have a history of security bugs: bpf, io_uring_*, userfaultfd, keyctl, ptrace, mounts and namespaces, kernel modules and others (SECCOMP_DENYLIST). It also makes clone3 fail with ENOSYS, so the C library falls back to clone, and refuses clone with namespace flags. Calls from another processor architecture (including x86-64's 32-bit-pointer x32 calls) kill the process. The server builds it at startup from judge/seccomp/gen.cpp with libseccomp, and bubblewrap installs it in each sandbox (--seccomp).

Limits are set with prlimit inside the sandbox (RUN_LIMITS): 128 processes and threads, 16 MB per file, no core dumps, and 10 s of CPU time per process (all its threads together; SIGKILL at 11 s). The CPU limit is a backstop to the 5 s wall-clock timeout, which on its own allows 5 s × cores of CPU. A run it stops is reported as Time Limit Exceeded with “CPU time limit exceeded”. The judge recognises it by bwrap's exit code 152, which is 128 + SIGXCPU. They're inside because the process count is per user namespace there; set outside, it would count every process the server's user owns. Killing a run on timeout kills everything in its sandbox. When the server runs as root (the cloud), sandboxes run as nobody, because root ignores the process limit. make sandbox-test checks all of this.

cgroup limits per submission (sandboxing step 7, VPS service only). A submission's compile and all its runs share one cgroup (Linux control group v2), with limits for the whole group rather than per process:

  • 768 MB of memory, including /tmp, and no swap;
  • 128 processes and threads;
  • one CPU's worth of CPU time (cpu.max 100000/100000).

Past the memory limit the kernel kills a process. That's reported with the usual status (Runtime Error, or Compile Error while compiling) and the message “Memory limit exceeded (768 MB for the whole submission…)”. At the limit the kernel first tries to reclaim memory, so a submission can also crawl until it runs out of time; if the cgroup's memory.events shows the limit was reached, the Time Limit Exceeded message says “Memory limit reached …, which slowed it down until it ran out of time”. The cgroup is killed and removed afterwards. It's on only when MAXRECALL_REQUIRE_CGROUPS=1, which the VPS's unit sets together with Delegate=yes and DelegateSubgroup=server; there the server refuses to judge if it can't set it up. Elsewhere (the cloud, make dev on Kubuntu) the server doesn't touch cgroups, and the Sandbox: line says so. Source: judge/cgroups.js, deploy/maxrecall-dsa.test.service.

Captured stdout/stderr is capped at 200,000 characters. The user's own prints are separated from the harness's result by a ###JUDGE_RESULT### marker line. Source: judge/runner.js (constants at the top, runCommand, spawnJudged, runFunctionSubmission, runProgramSubmission) and judge/sandbox.js (BASE_ARGS, RUN_LIMITS, sandboxedRun).

8. Where data lives

Every Submit is saved; Run is not. Each Submit writes one file:

users/<email>/submissions/<timestamp>.json

users/ is in the repo unless the MAXRECALL_USERS_DIR environment variable points elsewhere. The VPS uses /srv/maxrecall/data/users, outside its checkout, so git pull there never collides with its records. The server's first log line says which folder it's using.

All questions share that one folder; each record's question field says which question it was.

<email> is the signed-in user's email, lower-cased, taken from their session for each request, and checked against a strict pattern again before it's used in a path. <timestamp> is the UTC submit time with : replaced by -, e.g. 2026-10-29T03-27-46.194Z, so files sort by time. The file is written under a temporary name and then hard-linked into place with link(), so a crash never leaves half a record. Unlike rename(), link() refuses to replace an existing file, so two Submits in the same millisecond (from two tabs) produce a “not saved” warning rather than one overwriting the other.

Each user's queue and backlog (spaced-repetition plan, D1, D5, D6) are users/<email>/order.json, {schemaVersion: 1, submitsSinceLastIntroduced, queue: [{question, language, pass?, passesInARow}]}, the next question first, and users/<email>/backlog.json, {schemaVersion: 1, backlog: [{question, language}]}, the pairs waiting to come in, in order. question is the question's file name without .json; pass ("yes" or "no") is absent until the pair's first Submit, and passesInARow is 0 unless pass is "yes". A pair is in one file or the other, never both. At server start, before it listens, every user (a folder in users/ named by an email, holding submissions/ or profile.json) gets them: with neither file, an empty queue and a backlog of every pair the profile allows (languages turned off included), by question created, then file name, then the languages turned on in the learner's order, then the other allowed ones; otherwise the allowed pairs in neither file are appended to the backlog. With a chosen backlog (profile.json's "backlog": "chosen", step 13) nothing is ever appended, at start or at a Submit: a missing backlog.json is written empty, and the backlog holds only what make backlog-add put there; the consistency check then doesn't report pairs in neither file. order.js's backlogPairs is the rule. So, for a backlog "all", a new question, or a language newly allowed by hand, reaches it at the next restart. A file is written only if it's new or has changed, and each user gets a log line, e.g. Queues: owner@example.com: 0 in order.json, 26 in backlog.json (26 added). A user whose profile or queue files are invalid is left alone, logged, and refused Run and Submit (500) until the file is fixed. A saved Submit (since step 6; Run never) changes them, in this order: the pair is taken from where it is in the queue, or, from the backlog or neither file, starts at the front; pass becomes "yes" if Accepted, else "no", and passesInARow goes up by 1 or back to 0; the pair moves advance(passesInARow) places (that many others get ahead of it, or all of them); submitsSinceLastIntroduced goes up by 1; then introduceCount(…) pairs come from the backlog to the front of the queue, in backlog order, taking only pairs whose language is turned on and whose question still has that language (others stay where they are), and if any came, the counter goes back to 0. A user without both files at that moment gets them first, as at start. backlog.json is written before order.json, so a crash between them leaves a pair in neither file (put back in the backlog at the next start) rather than in both (which would refuse Run and Submit). GET /api/next (step 7) reads them, changing nothing. A question deleted from questions/ stays in them for now. At start, after filling them, the server runs the consistency check (make consistency-check) once and logs the totals, then a line per user with its counts and up to 10 of its errors and warnings (“…and N more: run make consistency-check”); info is only counted. It never stops the server. questions/renames.json, {"old-name": "new-name"}, is the rename log D5 describes; make rename-question (step 11) writes it, and the check reads it if it's there (it isn't a question: the server and questions.test.js leave it out). make recalculate-queue (step 12a) rewrites both from the records, leaving copies named order.json.before-recalculate-<UTC time> and backlog.json.before-… in the user's folder; nothing reads those. Edit these files by hand only with the server stopped: from step 6 on they change with every Submit, so a hand edit made while it runs can be overwritten. A feature, not a gap (owner, 2026-11-06): any question can be opened by its slug (problem.html?slug=…&language=…), chosen backlog or not, and its Submit or Skip puts it straight into the queue: that's how a learner queues a question of their choice (docs/how-to-put-a-question-directly-into-my-queue-by-slug.html). A chosen backlog limits what the list and Next offer; the profile's languages are what's enforced. Don't make Run, Submit or Skip refuse a question outside the queue or backlog (routes.js, checkExecutionRequest; guarded by a test in order.test.js). Source: order.js (recordSubmit), users.js, routes.js (prepareQueues, prepareUserQueues, loadQueueFiles, updateQueue).

Accounts and sessions are kept in auth/ (or MAXRECALL_AUTH_DIR), which is gitignored and created with owner-only permissions:

  • accounts/<email>.json: the email, the scrypt parameters (N=217, r=8, p=1, the OWASP minimum), a random salt and the hash. Never the password.
  • invites/<email>.json: an invite from make invite: the email, when it was made, when it expires (7 days later) and the code's SHA-256, never the code. A fast hash is enough because the code is 128 random bits. Deleted when used; a new invite for the same email replaces it.
  • sessions/<sha256 of token>.json: the email and the expiry time (360 days after login). The browser holds the random 256-bit token; the server keeps only its hash, so reading this folder doesn't give anyone a usable token.

Failed-attempt counts for throttling are kept in memory only, so restarting the server clears them. Source: auth.js.

users/ is gitignored (since 2026-10-30): submissions stay on the machine that recorded them, and the owner manages that folder by hand. nodemon ignores users/, so saving doesn't restart make dev. The other persistent state is the browser preferences above, which belong to one browser on one machine. Source: users.js, routes.js (handleExecution, /api/submissions).

10. Known gaps & caveats

Submitted code is sandboxed, but not fully hardened yet (docs/plans/sandboxing.md). Since step 4, compiling and running are both inside bubblewrap (see Judging), and make sandbox-test reports all 13 probes contained. Step 4 closed three gaps: compilers reading host files (#include, G7); the C++ compile timeout leaving cc1plus running (G10, measured at 137 s with a 1 s timeout before the fix); and compilers with no memory limit (a 257-byte template source went from 2 GB and growing to a Compile Error after 6.6 s). What's still open:

  • The VPS is slow to hand out fresh memory (measured 2026-11-03: 6 s for 200 MB in one process, erratic), so a legitimate submission that allocates a few hundred MB may occasionally run out of time there. The cause is a guess: the host overcommitting memory. (issue #23)
  • cgroup limits only in the VPS service (step 7). Elsewhere, memory is capped per language and CPU time per process, so a submission that forks gets those limits per process.
  • C++ runtime errors show no line number: a C++ exception carries no location, and a crash (e.g. a segfault) reports none. The other languages' runtime errors end in “(line N)” since 2026-11-03. (issue #26)
  • The reported runtime includes compiling and sandbox start-up, because runtimeMs is measured from before the compile. (issue #24)
  • The kernel is shared with the host, as with any namespace sandbox. (issue #22)

That's fine for the owner alone, and it's the remaining work before others are let in. The owner decided (2026-11-04) to let in invited testers they trust before then (limited live plan, D4), on condition that the VPS kernel is kept patched (#22). Source: judge/runner.js, judge/sandbox.js.

Found while planning the fix on 2026-11-02 (docs/plans/sandboxing.md §1): submissions inherited the server's whole environment, including MAXRECALL_PASSWORD (spawn passes process.env on by default). Since sandboxing step 1 they get only PATH and LANG, but they can still read the server's starting environment from /proc/<pid>/environ. That includes a password the VPS gets from EnvironmentFile=, though not one read from .env at runtime. They could also read questions/*.json, so hidden test cases' expected answers too; and a process a submission forked outlived the timeout. A Python submission that forked and called setsid() kept running after the judge gave up, and the judge reported 8042 ms instead of 5000, because the orphan held the output pipe open. Step 3 closed all three for runs (probes G1, G2, G5a and G5b contained).

  • A server started with no PATH couldn't sandbox anything (found 2026-11-03, not seen happen): judge/sandbox.js passes --setenv PATH with the server's own PATH to bwrap, which would be undefined, and spawn() refuses that. Every real way of starting it (a shell, systemd) gives it a PATH. Source: judge/sandbox.js (BASE_ARGS).
  • package-lock.json is gitignored, so the cloud and Kubuntu can install different dependency versions. npm's docs say it's meant to be committed.
  • Automated tests are few: unit tests for the spaced-repetition modules (advance.js, introduce.js, profile.js, order.js), users.js's user files, auth.js's invites and registering, the question files, and since 2026-11-06 the server's API through a real server (routes.test.js) (all make test), the judge's line-number test (make line-numbers-test), and the judge's escape test (make sandbox-test), which is a security check rather than a test of features. Nothing tests the pages automatically. routes.test.js doesn't cover the judge's busy 503 (JUDGE_BUSY, which needs 15 judgings at once), a Submit whose record or queue update fails to save, the bindings, or signing in beyond what the routes need (auth.test.js tests auth.js itself); scripts/characterize.js, run by hand, records the bindings and the sign-in answers.
  • Sign-in limits: no password reset or change: delete auth/accounts/<email>.json and make invite again. That leaves the account's existing sessions working (up to 360 days), because a session is checked against its own file, not the account (auth.js, sessionEmail); to end them too, delete the files in auth/sessions/ that name the email. Throttling is per email and in memory, so a restart clears it, and attempts spread over many emails aren't slowed. It remembers at most 10,000 emails (MAX_TRACKED_FAILURES, about 4 MiB), forgetting the one that failed longest ago. An email that isn't EMAIL_PATTERN or is over 238 characters (MAX_EMAIL_LENGTH, so its file names fit) is refused at once, costing no scrypt and leaving nothing to throttle. 12. Maintaining this file

This page only helps if it's kept true. Update it in the same commit as the change that makes it out of date. That includes:

  • adding, removing or renaming a file or directory → Layout;
  • adding or changing an endpoint → API;
  • a new or changed field in problem files → Problem file format;
  • a new language, toolchain, limit or judging rule → Judging;
  • a new localStorage key, CDN library or page → Front end;
  • anything stored on disk or in a database → Where data lives;
  • a toolchain installed or upgraded on either machine → Environments;
  • a gap fixed or found → Known gaps;
  • a design decision made, or a plan started or finished → Decisions & plans.

Conventions:

  • State only what the code actually does. Where a fact comes from code, name the file in a Source: line so it can be checked.
  • Mark anything unverified as a guess.
  • Bump “Last updated” at the top.
  • Keep the page self-contained: no external CSS, JS or fonts.
