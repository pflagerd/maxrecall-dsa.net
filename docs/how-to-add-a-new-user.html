Adding a new user

How to give someone, a tester included, an account on MaxRecall DSA: their languages and first questions, their invite, what to send them, and what to do later (more questions, a forgotten password, taking them off). Open this file straight from disk; it needs no server.

Status: written 2026-11-05, for the first testers of https://maxrecallcode.net (limited-live plan, steps 5 and 6). The first time through is a rehearsal, with a second email address of your own. Rehearsed 2026-11-06 in a copy of the VPS in the cloud (its maxrecall user, folders and service settings; no nginx, systemd or sandbox): steps 1 to 7 and every later change worked as written, after two fixes, the language menu (step 7) and archive/ (taking someone off). Updated 2026-11-06 for the shared login's removal (limited-live D3): step 5's message and what keeps strangers out.

The authorities are docs/deploy-vps.md (§4 invites, §11 a new tester, §13 the site and its sign-in limits) and readme.html, “Where data lives”; the code is auth.js (invites, registering), learner.js and scripts/learner-create.js (a new learner's files). This page explains them; where they disagree, they win.

What a user is

Two separate halves, made at different times:

HalfWhere (on the VPS)Made by
Their learning: languages, queue, backlog, Submit records/srv/maxrecall/data/users/<email>/You, with make learner-create (step 2), before they've done anything; a git repository from step 3
Their sign-in: a password hash, and sessions/srv/maxrecall/data/auth/accounts/<email>.json, auth/sessions/Them, registering with your invite (steps 4 and 6)

Both are named by their email in lower case: registering lower-cases it (auth.js, normalizeEmail), and so does make learner-create. Nothing comes before the app's own login page: the shared login nginx used to ask for first is gone (below).

Without step 2 a new user still works, but with no profile.json they get every question in all five languages waiting for them ("backlog": "all"). Step 2 gives them only the languages and questions you choose.

The steps, for a tester on the VPS

  1. Decide their email, languages and first questions
  2. Set them up: make learner-create
  3. Make their folder a git repository
  4. Make their invite: make invite
  5. Send them what they need
  6. They register
  7. Check it as them

Then: on Kubuntu, later changes, your own account, what keeps strangers out, what testers can and can't do and the checklist.

All the VPS commands are run as root on the VPS, srv702017.hstgr.cloud, from the service's checkout:

cd /srv/maxrecall/maxrecall-dsa.net

The server keeps running for all seven steps.

1. Decide their email, languages and first questions

  • Their email, exactly as they'll type it when registering (case doesn't matter). It's their username in the app.
  • Their languages: one or more of javascript, python, cpp, java, d. The first is their default. They can't turn on any others.
  • Their first questions, in the order they'll get them. Several: questions added later only come in at their next Submit or Skip. To see every question's name:
sudo -u maxrecall env MAXRECALL_USERS_DIR=/srv/maxrecall/data/users make backlog-show EMAIL=daniel.pflager@gmail.com
  • Lists your own queue and backlog, then every question with where its pairs are. It only reads. Any existing user's email will do.

2. Set them up: make learner-create

First a dry run, which writes nothing:

sudo -u maxrecall env MAXRECALL_USERS_DIR=/srv/maxrecall/data/users make learner-create EMAIL=tester@example.com LANGUAGES=python SLUGS="hello-world two-sum" DRY_RUN=1
  • sudo -u maxrecall: as the service's user, so the files are its own (sudo(8)).
  • env MAXRECALL_USERS_DIR=…: the service's users folder. Without it the files would go into the checkout's own users/, which the service never reads.
  • EMAIL, LANGUAGES ("python java" for two) and SLUGS (quoted, separated by spaces): from step 1. Each question goes in once for each of their languages it has.
  • DRY_RUN=1: shows the profile.json and backlog it would write.

If it's right, the same without DRY_RUN=1:

sudo -u maxrecall env MAXRECALL_USERS_DIR=/srv/maxrecall/data/users make learner-create EMAIL=tester@example.com LANGUAGES=python SLUGS="hello-world two-sum"
  • Writes their folder with profile.json (allowed.languages, and "backlog": "chosen": the server adds nothing to their backlog by itself), an empty order.json and their backlog.json, all at once.
  • It refuses, changing nothing, if their folder exists already: they're set up, or have used the app. See later changes instead.

Check it (only reads):

sudo -u maxrecall env MAXRECALL_USERS_DIR=/srv/maxrecall/data/users make backlog-show EMAIL=tester@example.com
  • The first line should say backlog "chosen"; languages turned on: python, then an empty queue and their questions in the backlog.

3. Make their folder a git repository

So their work has a history, and can be copied off the VPS (limited-live D5, the owner's idea). Their folder now holds only its three starting files, so the first commit is small.

cd /srv/maxrecall/data/users/tester@example.com
sudo -u maxrecall git init -b master
  • Every git command as maxrecall, who owns the folder. Run as root, .git would be root's, and maxrecall couldn't commit to it later; and git refuses to work as root in a repository another user owns (“detected dubious ownership”, git's safe.directory check; tested with git 2.43.0, Ubuntu 24.04's).
  • -b master names the first branch, so it matches the push below whatever git's default is (git-init).
printf '*.tmp-*\n' | sudo -u maxrecall tee .gitignore >/dev/null
  • The server writes each file as <name>.tmp-<number>, then renames it into place (users.js, writeUserFile); this keeps a half-written one out of any commit. tee writes the file as maxrecall (a plain > would write it as root).
sudo -u maxrecall git config user.name "MaxRecall VPS"
sudo -u maxrecall git config user.email "maxrecall@srv702017.hstgr.cloud"
  • Who the commits are by, for this repository only. maxrecall has none, and without one the commit stops with “Please tell me who you are”. It's only a label; the address needn't receive mail.
sudo -u maxrecall git add .
sudo -u maxrecall git commit -m "new user initial commit"
  • Should commit .gitignore, backlog.json, order.json and profile.json. The app ignores the .git folder: it only reads the files it knows (checked with make consistency-check: “nothing found”).

Then copy it to Kubuntu [Kubuntu]

Kubuntu pulls from the VPS (limited-live D5, option B, owner's choice, 2026-11-05). Nothing is pushed from the VPS and it holds no credentials, so there's no git remote add or git push on the VPS, and testers' data stays on your own machines. In a folder of your choosing outside the app's checkout, say ~/maxrecall-backups/vps-users:

mkdir -p ~/maxrecall-backups/vps-users
git clone --upload-pack='sudo -u maxrecall git-upload-pack' -c remote.origin.uploadpack='sudo -u maxrecall git-upload-pack' root@srv702017.hstgr.cloud:/srv/maxrecall/data/users/tester@example.com ~/maxrecall-backups/vps-users/tester@example.com
  • You connect as root, but the repository is maxrecall's, and git on the VPS refuses to send it to root (“detected dubious ownership”). --upload-pack='sudo -u maxrecall git-upload-pack' makes the VPS run git's sending side as maxrecall instead (git-clone). Root needs no password for sudo.
  • -c remote.origin.uploadpack=… saves the same in the copy, for every later pull: --upload-pack on its own is used for the clone only, and a later git pull is refused again (tested).
  • The @ in the email is fine: only the part before the : is read as user and host (tested 2026-11-04).

Later, to bring their new commits over:

git -C ~/maxrecall-backups/vps-users/tester@example.com pull --ff-only

Or every user at once:

for d in ~/maxrecall-backups/vps-users/*/; do git -C "$d" pull --ff-only; done
  • --ff-only: the copy only ever follows the VPS, so a pull that would need a merge is refused rather than made.

Tested (cloud, git 2.43.0) with a repository owned by another user, over file://, which uses the same upload-pack setting as SSH:

  • a plain clone as root was refused (“dubious ownership”);
  • the clone above worked;
  • after a new commit on the VPS side, a plain git pull --ff-only brought it over.

Not tested over real SSH to the VPS.

With git-nested (your own tool): whatever it runs to fetch from the VPS must run git's sending side as maxrecall there, as these commands do, or it gets the same refusal.

Not yet automatic: this step commits only the starting files. Their later work reaches their repository only once something commits it periodically on the VPS: issue #64. Until then, a pull brings over only this first commit.

4. Make their invite: make invite

sudo -u maxrecall env MAXRECALL_AUTH_DIR=/srv/maxrecall/data/auth make invite EMAIL=tester@example.com
  • MAXRECALL_AUTH_DIR (sign-in data) this time, not MAXRECALL_USERS_DIR (learning data).
  • It prints a code, shown only now: only its SHA-256 is stored. It works once, for this email only, for 7 days.
  • It refuses if you're not the user who owns the sign-in folder, so the server can always read the invite. Run as root without sudo -u maxrecall, it says so.
  • Lost or expired: run it again. A new invite replaces the old one; their folder doesn't change.

5. Send them what they need

Three things: the address, their code, and the email to register with. A draft, to edit before sending. It also says what's stored about them (the limited-live plan's D5: a note to testers). That's a courtesy, not legal advice: whether anything more is needed depends on where they live.

Hello,

You're invited to try MaxRecall Code, a site I'm building to learn,
practice and recall coding, data structures and algorithms. It's
early, so expect rough edges, and please tell me about them.

1. Open https://maxrecallcode.net and choose Register.
2. Enter:
     email:       tester@example.com   (exactly this one)
     invite code: PASTE-THE-CODE-HERE  (works once, for 7 days)
     password:    one of your own, at least 12 characters
3. You'll see your list of questions. Where a question has a
   Learning tab, read it first.

What's kept: your email, a hash of your password (never the password
itself), and what you submit (your code, results and times), on my
server. I can read all of it; nobody else is given it. Tell me if you
want it deleted.

Thanks!
  • The code is the only secret in it, and it's limited: it works once, only with this email, for 7 days. If it may have leaked before they used it, make a new one (step 4): that replaces it.
  • Testers sent the older message, before 2026-11-06, were told of a shared username and password first: there's no such prompt any more, and nothing to do about it.

6. They register

At https://maxrecallcode.net/login.html#register: email, invite code and a password of their own (at least 12 characters). Registering signs them in, deletes the invite, and shows their list. Sessions last 360 days.

Every refusal gives one message, “Registration isn't open for that email and invite code.”, whatever the reason: a wrong email, a wrong or expired code, a used one. That's deliberate (it reveals nothing to someone guessing). The usual causes: a different email from the one invited, or a code copied with a character missing. A too-short password gets its own message. After 5 refusals for one email, each try waits longer (up to 15 minutes); restarting the server clears that.

7. Check it as them

For the rehearsal with your own second email, or to see what a tester sees: open https://maxrecallcode.net/login.html#register in a private window. In a normal window the new sign-in would replace yours: browsers keep one cookie per site.

  • The header shows their email.
  • The list shows their chosen questions, in their languages, marked new.
  • The language menu offers only their languages.
  • There's no Test button: that's only yours (MAXRECALL_USER).

On Kubuntu (your own machine)

The same two commands, without sudo or env: on Kubuntu the folders are the checkout's own users/ and auth/.

make learner-create EMAIL=tester@example.com LANGUAGES=python SLUGS="hello-world two-sum"
make invite EMAIL=tester@example.com
  • Step 3 the same way, in users/tester@example.com, as yourself: git init -b master, the .gitignore, git add . and git commit. Your own git identity is used, so no git config. The app checkout's own .gitignore leaves users/ out (/users/), so the checkout's git never sees the learner's repository inside it.
make dev
  • Then register at http://localhost:3000/login.html#register. Nothing comes before the login page, on Kubuntu as on the VPS.

Later changes

More questions

The server must be stopped for this (a Submit rewrites backlog.json too), so the site is down for everyone for those seconds:

systemctl stop maxrecall-dsa.test.service
sudo -u maxrecall env MAXRECALL_USERS_DIR=/srv/maxrecall/data/users make backlog-add EMAIL=tester@example.com SLUGS="climbing-stairs" DRY_RUN=1
  • AT=1 puts them at the front of the backlog instead of the end. If Backlog after (…) is right, run it again without DRY_RUN=1. make backlog-remove takes questions out the same way.
systemctl start maxrecall-dsa.test.service

What's added comes into their queue at their next Submit or Skip (docs/deploy-vps.md §10).

The invite ran out before they registered

Run step 4 again, and send the new code.

A forgotten password

There's no reset page. Delete their account, and invite them again. Their learning (queue, records) is untouched:

rm /srv/maxrecall/data/auth/accounts/tester@example.com.json
  • That signs them out everywhere, at once: a session counts only while its account exists, and only if it's newer than the account, so registering again doesn't bring old sessions back either (auth.js, sessionEmail; since 2026-11-06, #104). Each old session's file is deleted the next time a browser presents it; one never presented again stays in auth/sessions/, unusable.
  • Until #104 this step also deleted their session files, because a deleted account's sessions kept working, for up to 360 days. That's no longer needed.

Then step 4 (a new invite) and steps 5–6 (they register again, with a new password).

Taking someone off

Remove their account (the rm just above), which signs them out everywhere, then put their learning folder aside rather than deleting it:

mv /srv/maxrecall/data/users/tester@example.com /srv/maxrecall/data/archive/tester@example.com.$(date -u +%Y%m%dT%H%M%SZ)
  • Into archive/, outside users/: the server counts every folder in users/ named like an email as a user. date -u +… adds the UTC time to the name (docs/deploy-vps.md §10).
  • archive/ must exist. It does on the VPS (made in docs/deploy-vps.md §10), but make deploy-server doesn't make it, and without it mv stops with “No such file or directory”, moving nothing. On a new machine, make it first, owned by the service's user and closed to others: install -d -o maxrecall -g maxrecall -m 750 /srv/maxrecall/data/archive (install(1): -d makes the folder, -o/-g its owner and group, -m its permissions).
  • No server stop needed: with their account gone, none of their sessions works, so nothing can ask for their files any more.
  • If they asked for their data to be deleted, delete the archived folder too (and any copy on Kubuntu).

Your own account

Through the SSH tunnel's trusted port you need none: every request there is you. On the public site you do, like anyone else. Your learning folder already exists, so skip step 2: make invite EMAIL=daniel.pflager@gmail.com (step 4), then register. Step 3 applies to your folder too; its first commit then holds your records so far. Being MAXRECALL_USER gives you the Test button there too.

What keeps strangers out: no shared login since 2026-11-06

Until 2026-11-06 nginx asked every visitor for one shared username and password before the app (the limited-live plan's D3). It's gone, from the configuration and from the VPS (docs/deploy-vps.md §13, step 8): anyone can reach the login page. What stops a stranger now:

  • Registering needs an invite: only an email you ran make invite for, with its code, once, within 7 days (auth.js; step 4).
  • Failed sign-ins slow down per email: after 5, each try waits longer, up to 15 minutes (auth.js; step 6).
  • nginx limits login and register attempts per visitor (an IPv6 /64 counts, roughly, as one) and for the whole site (deploy/nginx-maxrecallcode.conf, docs/deploy-vps.md §13).

So there's no username or password to send, change or take away besides each person's own sign-in. To take someone off: later changes, “Taking someone off”.

What testers can and can't do

  • They can use only their languages: the menu offers no others, and the server refuses Run and Submit in any other (403).
  • Their list and Next offer only their chosen questions, but they can open any question by its address (problem.html?slug=…), and a Submit or Skip then puts it in their queue. That's a feature (owner, 2026-11-06): how a learner queues a question of their choice (how-to-put-a-question-directly-into-my-queue-by-slug.html). Their profile still limits the languages.
  • Only you can Test.
  • Their code runs in the judge's sandbox (readme.html, “Judging”). You decided to let testers you trust in before the remaining sandbox work (limited-live D4).
  • Until there's a backup (limited-live D5), their work exists only on the VPS.
