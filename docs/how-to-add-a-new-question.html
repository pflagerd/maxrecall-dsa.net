Adding a new question

How to write a question file for MaxRecall DSA by hand, check it, try it, and give it to learners. Open this file straight from disk; it needs no server.

Status: written 2026-11-05 and being followed for the first time, with a question about singly linked lists as the example (below). Where following it shows a step is wrong or missing, the step gets fixed here, in the same pull request as the question.

The authority for the file format is readme.html, “Problem file format”, and question-files.js's checkQuestion, which make test runs. This page explains them; where they disagree, they win.

The steps

  1. Decide what the question is
  2. Start a branch
  3. Create the file from the template
  4. Fill in the fields
  5. Write the test cases
  6. Run make test
  7. Try it in the app, with Run and Test
  8. Commit and open a pull request
  9. After it's merged: deploy, and give it to learners

Then: the field reference, the checklist and the worked example.

1. Decide what the question is

Before any file, decide:

  • What it teaches. One new concept, stated in a sentence. It may build on a concept an earlier question taught, ideally at most one: list that question in alreadyLearned, and link it in the Learning tab's “Learned earlier”. A question that needs two new concepts is two questions, the one the other depends on first.
  • Its name (the slug): lowercase letters and digits, joined by single hyphens, e.g. linked-list-from-values. It's the file name (questions/<name>.json), part of the page's address (problem.html?slug=…), and how every learner's queue refers to it, so pick one you won't want to change. (If you must, make rename-question does it safely.)
  • Its title, as the problem list shows it.
  • Its difficulty: Fundamentals, Easy, Medium or Hard. Fundamentals is for a question whose new concept is a feature of the language or its library; the rule is in docs/roles/questions/how-to-write-a-question.md, section 1.
  • Its topics and sources: names shown as bubbles. Use names already in labels.json where they fit, so the colours match; a new name works, in the default colours, until it's added there.
  • How it's judged (judgeMode): "function", the judge calls one function with arguments and compares what it returns; or "program", the judge runs the whole program with some standard input and compares its output. Most questions are functions.
  • Its languages. Each language needs its own starter code, function name, description, examples and constraints, and C++, Java and D also a type signature. Starting with one language and adding the others later is fine: a language left out is simply not offered.

What the judge can pass in. Arguments reach the function exactly as JSON gives them: numbers, text, true/false, null, lists and objects. A function can return an object of its own (a linked list node, say): the judge turns it into JSON from its attributes. But it can't receive one: a linked list given as an argument would arrive as a plain dictionary. So for now, a linked list question has the learner build a list and return it. (Source: judge/runner.js, the Python harness.)

2. Start a branch

Every change goes through a pull request, on a branch of its own. In your Kubuntu checkout:

git switch master
git pull --ff-only
  • switch master goes to the main branch; pull --ff-only brings it up to GitHub's, refusing to make a merge (git-pull).
git switch -c question-linked-list-from-values
  • -c creates the branch and switches to it (git-switch). Name it after the question.
make test
  • Should pass before you start, so that any failure later is yours.

3. Create the file from the template

Copy docs/question-template.json to your question's file, and change it. The template is the Python parts of singly-linked-list-hello-world.json, a working function-mode question with a node class, so a copy starts out valid and you change it rather than write it from nothing (owner's suggestion, 2026-11-05). It lives in docs/, not questions/: every file in questions/ is a question, listed and given to learners.

cp docs/question-template.json questions/linked-list-from-values.json
  • cp SOURCE DEST copies the file (cp). Use your question's name in place of linked-list-from-values.

4. Fill in the fields

The field reference has every field. Notes on the ones that need care:

created

When you created the question, in UTC, to the second. It decides where a new question goes in a backlog filled in creation order. Get it from:

date -u +%Y-%m-%dT%H:%M:%SZ
  • -u: in UTC. +FORMAT: in this format, e.g. 2026-11-05T19:04:31Z (date).
Or here, now: —

description, examples, constraints

  • description is HTML: <p>, <code>, <strong>. Say what the function gets and what it must return, including the edge cases (an empty list, say). Maths between $…$ is drawn by KaTeX.
  • examples: each has input and output as text, shown as written, and an optional explanation. Use the visible test cases.
  • constraints: a list of short lines, e.g. "0 ≤ len(values) ≤ 1000". It may be empty, [], but must be there.

starterCode and functionName

  • The starter code is what the editor holds when a learner opens the question: the function, with pass as its body, and any class it needs (a node class, say).
  • functionName must be exactly the function's name in the starter code. If it's missing or wrong, every Run in that language fails with NameError.

5. Write the test cases

Each test case is { "args": [ … ], "expected": …, "hidden": true or false }:

  • args: the arguments, in order, as a JSON list, even for one argument: [[1, 2, 3]] is one argument, the list [1, 2, 3].
  • expected: what the function must return, as JSON. Python's None is null.
  • hidden: false for a case the learner sees, and Run runs; true for one only Submit and Test use. At least one must be visible.

Cover: the ordinary case; the smallest inputs (empty, one item); something larger; and anything the description singles out. Make the visible ones the examples, and hide the edge cases, so passing means understanding rather than matching what was shown.

Returning an object. The judge compares a returned object by its attributes, by name, in any order, and the set of names must be the same (judge/runner.js, deepEqual). For a node class with value and next, the list 1 → 2 is expected as

{ "value": 1, "next": { "value": 2, "next": null } }

So a learner who adds an attribute of their own (self.size, say) fails every case. Say so in the description.

6. Run make test

make test

Among its tests, one per question file checks it against the format (questions.test.js): a misspelt field name, a language with no function name, a test case without expected, all test cases hidden, and so on. A failure names the field, e.g.

functionName.python is missing: starterCode has python

It doesn't check that your expected answers are right. That's step 7.

7. Try it in the app, with Run and Test

make dev
  • Starts the app on http://localhost:3000 and restarts it when a file changes. Sign in as yourself (MAXRECALL_USER). If you have no account on this machine yet: make invite EMAIL=<your email>, then Register on the login page with the code it prints.

Open the question directly (it isn't in your backlog):

http://localhost:3000/problem.html?slug=linked-list-from-values&language=python
  1. Read it as a learner would: the description, examples and constraints.
  2. Run the starter code unchanged: every visible case should fail, not crash the page.
  3. Write a correct answer and press Test (shown to you only). It judges every case, hidden ones shown in full, and records nothing. Every case should pass. One that doesn't means a wrong expected, or a wrong answer.
  4. Write a plausible wrong answer (forgetting the empty list, say) and Test again: the cases meant to catch it should fail.

Avoid Submit here: it records a result in your local users/ folder.

8. Commit and open a pull request

git add questions/linked-list-from-values.json
git commit -m "Add question: Linked List from Values"
git push -u origin question-linked-list-from-values
  • -u remembers GitHub's copy as this branch's, so later pushes need no names (git-push).

Then open the pull request on GitHub, for review before merging.

9. After it's merged: deploy, and give it to learners

Deploy it on the VPS with the guarded deploy (docs/deploy-vps.md, “The quick way”, “Updating: the guarded deploy”), after the owner's yes for the commit. The yes names one commit by its id, and the deploy puts exactly that commit live, or stops if master has moved past it (docs/decisions/20261108T085607-0800-guarded-deploy.md). A plain git pull and make deploy-server would deploy whatever master's tip is, including commits merged after the yes.

  • Learners whose backlog is "all" get it at that restart.
  • Learners with a chosen backlog (you, and testers set up with make learner-create) get it only when it's added, with the server stopped (docs/deploy-vps.md §10):
sudo -u maxrecall env MAXRECALL_USERS_DIR=/srv/maxrecall/data/users make backlog-add EMAIL=daniel.pflager@gmail.com SLUGS=linked-list-from-values

Worked example: a singly linked list question

Decided 2026-11-05 (owner): a question that reinforces singly linked lists, from what the judge supports today, in Python only to begin with. The question file itself is the owner's to write, following the steps above; it's reviewed, and this section filled in, as it's done.

  • What it teaches: building a singly linked list from a list of values, keeping a pointer to the tail so each append is one step, and that an empty list of values gives no list at all (None). The step after singly-linked-list-hello-world, which builds a fixed two-node list.
  • Proposed: name linked-list-from-values; title “Linked List from Values”; Easy; topics ["Linked List", "Singly Linked List"] (both in labels.json); sources []; function mode; Python only.
  • The function: it takes a Python list of values and returns the head of a new list holding them in order, using the node class from the hello-world question, with attributes value and next.
