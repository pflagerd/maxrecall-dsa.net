# Submission records go to version 4: each says its `kind`, and a fill-in answer is kept in `answer`

2026-11-08 · decided by the owner · written by users

**Decided** (owner, 2026-11-08, in the users session; #160's Q11, which
was users'), each as users recommended in
`docs/plans/submission-records-v4.md`:

- **D1 (a)**: a non-code answer is kept as `answer`, the kind's own
  object as the request sent it (e.g. `{ "blank": "\\'" }`); a code
  question keeps `code`, as #160's Q5 decided.
- **D2 (a)**: every version 4 record says its `kind`.
- **D3 (a)**: the judge's `message` and `hints` are kept when given.
- **D4 (a)**: fields a fill-in judge doesn't produce (`passed`, `total`,
  `runtimeMs`, `stdout`, `stderr`) are `null`, and `results` is `[]`, as
  for a Skip.
- **D5 (a)**: #88's refresher mark (`refresher: "yes"`) joins version 4
  if #88 resumes before this is built; otherwise it's version 5.
- **D6 (a)**, after questions 2's review, for #160's Q6.4: a fill-in
  record also keeps `judgeSha256`, the SHA-256 of
  `questions/<slug>.judge.js`; `questionSha256` stays the `.json`
  file's alone, so each hash shows which file changed.
- **D1 kept as sent** (owner, after questions 2 suggested storing the
  answer as the server validated it): the answer object is stored as
  the request sent it. Q8's `maxLength` is still checked before judging.

Records of versions 1 to 3 aren't rewritten. Nothing is built yet: it
follows questions' side of #160 (its B7).

**Why**: Q5 kept `code` for code questions, so every existing record and
reader of `code` stays as it is. A record that names its kind can be read
without its question file, whose kind may change. The consistency check
and `make recalculate-queue` read only `status` and `skipped`, which a
fill-in record fills as a code one does (Q9), so they don't change.
