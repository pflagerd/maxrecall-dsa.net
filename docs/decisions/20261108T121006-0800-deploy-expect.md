# `make deploy-server` can be told which commit to deploy: `DEPLOY_EXPECT`

2026-11-08 · decided by the owner · written by infrastructure and security

**Decided** (owner, 2026-11-08: "Go ahead with DEPLOY_EXPECT"; proposed
by this role in #151): `scripts/deploy-server.sh` takes an optional
`DEPLOY_EXPECT=<full commit id>`. With it, the script deploys only if
`master` on GitHub is exactly that commit, and otherwise stops with
nothing changed. The guarded deploy (`docs/deploy-vps.md`, "The quick
way", "Updating: the guarded deploy", step 4) sets it to the commit the
owner said yes to. Adds to
`20261108T085607-0800-guarded-deploy.md`, whose "What it can't close"
this closes.

**Why**: the guarded deploy checked `master` in root's checkout, then the
script fetched `master` again into `/srv`, and its `git pull` fetched a
third time. A merge in those seconds went live unapproved (a
time-of-check-to-time-of-use gap). Now the script fetches once, compares
`FETCH_HEAD` with the id, and runs `git merge --ff-only <id>` instead of
`git pull`, so what's checked is what's deployed.

**Still "no pinning"** (owner, 2026-11-07): it never deploys an older
commit. It deploys the tip of `master` when the tip is the approved
commit, and refuses otherwise.

**Choices made** (small, stated rather than asked):
- **Optional**: without it the script behaves as before, so a by-hand
  run and §8 still work.
- **A full 40-character lowercase id only**, checked before anything
  else: a short id can be ambiguous, and anything else (an option like
  `--upload-pack=…`, a branch name) is refused, so the value can't be
  read as something other than a commit.
- **Passed through the `sudo` re-run** (the script's line naming the
  variables `sudo` keeps), since `sudo` drops the rest of the environment.
- **First install**: clones, then checks `HEAD`; a mismatch stops before
  packages, the unit file or the service.

**Checked** in a mount namespace (`unshare --mount`) with throwaway
`/etc/systemd/system`, `/srv`, `/run/systemd`, a bare repository as
GitHub, and stand-ins for `systemctl`, `journalctl`, `ss`, `curl`,
`npm`, `adduser`, `runuser`, `id` and `sudo` (`sudo` passing on only its
`NAME=value` arguments, as `env_reset` does). Real git and the real
script. Ten cases: first install and update with and without it; a stale
id refused with the service untouched; a short id, an option-like value
and uppercase refused before any change; through the `sudo` re-run; a
stale id on a first install stops before installing. Then the `sudo`
line broken on purpose: the stale-id case deployed an unapproved commit
with exit 0, so the test catches that. Not tested: the real VPS and
systemd.

Source: `scripts/deploy-server.sh` (`EXPECT`, the `sudo` line, §4's
block), `docs/deploy-vps.md` ("The quick way"; "Updating: the guarded
deploy", "The gap" and steps 4–5).
