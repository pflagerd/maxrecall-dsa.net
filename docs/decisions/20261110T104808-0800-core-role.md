# The users role and the infrastructure and security role become one: core

2026-11-10 (UTC) · decided by the owner · written by the architect

**Decided** (owner, 2026-11-10, about 18:44 UTC, in the architect's
session). The owner proposed merging the two roles into one named
"supervisor" and asked for feedback. The architect recommended merging
only with a review rule in place of the boundary lost, and a name that
says what the role owns. The owner's answer:

> 1. Merge with the review rule; architect does the reviews; new role
> messages architect directly when review needed.
> 2. Let's use the name core
> 3. architect does the senstive-path reviews, triggered by core when
> core detects a need or when architect recognizes a need, either or
> both.

**What it changes.**

- A new role, **core** (`docs/roles/core.md`), owns everything the users
  role and the infrastructure and security role owned. Their role files
  become stubs that point to it. Their handoff folders are history;
  core's is `docs/session-handoff/core/`.
- **Sensitive paths**: the architect reviews every pull request that
  touches `server.js`, `auth.js`, `paths.js`, the sandbox
  (`judge/sandbox.js`, `judge/seccomp/**`, `judge/cgroups.js`),
  `deploy/**`, `scripts/deploy-server.sh` or `.github/workflows/`,
  before the owner merges it. Core asks by message; the architect also
  checks core's pull requests itself (`docs/roles/core.md`, "Sensitive
  paths"; `docs/roles/architect.md`, "Reviews").
- `docs/contracts.md`: each contract's parties name core. Contracts 9
  and 11, and part of 7, are now inside one role; they are kept, as
  contract 8 was, because what each side relies on is still true.
- `CLAUDE.md` (the roles table, examples) follows in its own pull
  request.

**Why merge** (the architect's reading; the owner gave no reason in
words): recent work kept crossing the line between the two roles (the
test question bank: PR 204 and PR 217; records version 4: PR 209 and
Issue 160's step 2(b)), three contracts were mostly between them, and
it is one fewer session for the owner to start and steer.

**Why the review rule.** `server.js` was split on 2026-11-05 (Issue 76)
so that the sign-in layer was one role's and the feature routes
another's. With one role owning both, a feature change and a change to
the gate could go in one pull request with no second role looking. The
review stands in for that boundary.

**The architect's additions, not the owner's words** (each can be
changed): `judge/cgroups.js` is on the list as part of the sandbox; a
pull request that touches a sensitive path stays a draft until the
review is in it; core may run numbered sessions (`core-1`, `core-2`)
when both kinds of work are live.

**The name.** The owner's choice. In this project "core" means the
application and the site it runs on: everything but what questions say
and how answers are judged (questions'), and coordination (the
architect's).

**Replaces** Issue 164, the proposal to merge infrastructure and
security into the architect's role, which is no longer the plan.

**Left as history**: dated plans, decision files, the readme's Decisions
rows and the two old handoff folders keep the old role names. Files that
are now core's and name the old roles in the present tense
(`docs/deploy-vps.md`, `.github/workflows/uptime.yml`, comments in
source) are core's to bring up to date.

Source: `docs/roles/core.md`; the owner's messages in the architect's
session of 2026-11-10.
